Nível 1 · Iniciante

Os fundamentos

Aqui você parte do zero absoluto. Ao final, terá o Git instalado, entenderá o que é um commit e terá publicado seu primeiro projeto no GitHub.

1.1

O que é Git e o que é GitHub

Git é um programa que você instala no seu computador. Ele registra cada versão dos seus arquivos ao longo do tempo, para que você possa ver o que mudou, quem mudou e voltar atrás quando algo der errado.

GitHub é um site que guarda os seus projetos Git na nuvem. Ele permite que várias pessoas trabalhem no mesmo projeto, revisem o trabalho umas das outras e mantenham uma cópia segura fora do seu computador.

AnalogiaO Git é como o “salvar jogo” de um videogame: você cria pontos de salvamento e pode voltar a qualquer um deles. O GitHub é a nuvem onde esses saves ficam guardados e podem ser compartilhados com o seu time.
GitGitHub
O que éPrograma de controle de versãoServiço online que hospeda repositórios Git
Onde rodaNo seu computadorNa internet (github.com)
Precisa de internet?NãoSim
Para que serveRegistrar versões dos arquivosCompartilhar, colaborar e fazer backup

Palavras que você vai ouvir muito

  • Repositório (repo): a pasta do projeto que o Git está acompanhando.
  • Commit: um ponto de salvamento, com uma mensagem explicando o que mudou.
  • Branch: uma linha paralela de trabalho (você verá no nível 2).
  • Remoto: a cópia do repositório que fica no GitHub.
1.2

Instalando o Git

Windows

Baixe o instalador em git-scm.com/downloads e avance com as opções padrão. Ele instala também o Git Bash, um terminal onde você vai digitar os comandos deste guia.

macOS

Abra o app Terminal e digite git --version. Se o Git não estiver instalado, o sistema oferece instalar as ferramentas de desenvolvedor. Outra opção é usar o Homebrew:

Terminal
brew install git

Linux (Ubuntu/Debian)

Terminal
sudo apt update
sudo apt install git

Confirme que deu certo

Terminal
git --version
# Resposta esperada, algo como: git version 2.47.0
DicaO terminal parece assustador, mas é só um lugar para digitar ordens ao computador. Digite o comando, aperte Enter e leia a resposta.
1.3

Configuração inicial

Antes do primeiro commit, diga ao Git quem você é. Esse nome e e-mail ficam gravados em cada commit que você fizer. Você só precisa fazer isso uma vez por computador.

Terminal
git config --global user.name "Seu Nome"
git config --global user.email "seu.email@empresa.com"

# Faz todo repositório novo começar na branch "main"
git config --global init.defaultBranch main

# Confira o que ficou configurado
git config --list
AtençãoUse o mesmo e-mail da sua conta do GitHub. Assim, seus commits aparecem ligados ao seu perfil.
1.4

As três áreas do Git

Este é o conceito mais importante do nível 1. Todo arquivo passa por três lugares antes de virar parte do histórico:

  1. Pasta de trabalho: onde você edita os arquivos normalmente.
  2. Área de preparação (staging): onde você escolhe quais mudanças vão entrar no próximo commit, usando git add.
  3. Repositório: o histórico permanente. As mudanças chegam aqui com git commit.
AnalogiaPense em uma mudança de casa. A pasta de trabalho é o seu quarto bagunçado. O staging é a caixa onde você coloca o que vai levar. O commit é fechar a caixa com fita e escrever uma etiqueta.
1.5

Seu primeiro repositório e commit

Vamos criar uma pasta, transformar em repositório e salvar a primeira versão.

Terminal
# 1. Crie uma pasta e entre nela
mkdir meu-projeto
cd meu-projeto

# 2. Transforme a pasta em um repositório Git
git init

# 3. Crie um arquivo
echo "# Meu primeiro projeto" > README.md

# 4. Veja o que o Git percebeu
git status

# 5. Coloque o arquivo na área de preparação
git add README.md

# 6. Salve no histórico com uma mensagem
git commit -m "Cria o README do projeto"

O comando git status é o seu melhor amigo. Use sempre que tiver dúvida: ele mostra quais arquivos mudaram, quais estão preparados e o que fazer em seguida.

Dicagit add . (com ponto) adiciona todas as mudanças da pasta de uma vez. É prático, mas confira antes com git status para não incluir algo sem querer.
1.6

Vendo o histórico e as diferenças

Terminal
# Lista os commits, um por linha
git log --oneline

# Mostra o que mudou e ainda não foi para o staging
git diff

# Mostra o que está no staging e vai entrar no próximo commit
git diff --staged

# Mostra os detalhes de um commit específico
git show a1f3c2d

Cada commit tem um código único (o hash), como a1f3c2d. Você usa esse código para se referir a um commit específico. Para sair de telas longas como a do git log, aperte a tecla q.

1.7

Enviando seu projeto para o GitHub

  1. Crie uma conta gratuita em github.com.
  2. Clique em New repository, dê um nome (ex.: meu-projeto) e crie sem marcar a opção de README, já que você já tem um.
  3. Conecte seu repositório local ao GitHub e envie:
Terminal
# Liga a pasta local ao repositório no GitHub (troque pelo seu usuário)
git remote add origin https://github.com/seu-usuario/meu-projeto.git

# Envia a branch main e memoriza o destino
git push -u origin main
Senha não funcionaO GitHub não aceita a senha da conta no terminal. Use um token de acesso pessoal (Settings → Developer settings → Personal access tokens) no lugar da senha, ou instale o GitHub CLI e rode gh auth login, que faz tudo por você.

Depois do primeiro envio, basta git push para mandar novos commits.

1.8

Baixando projetos: clone e pull

Clone baixa um repositório inteiro do GitHub para o seu computador, pela primeira vez. Pull traz as novidades de um repositório que você já tem.

Terminal
# Primeira vez: baixa o projeto todo
git clone https://github.com/seu-usuario/meu-projeto.git

# No dia a dia: atualiza com o que os colegas enviaram
git pull
Rotina recomendadaComece o dia com git pull. Trabalhe, faça commits pequenos, e termine com git push.
1.9

O arquivo .gitignore

Alguns arquivos nunca devem ir para o repositório: senhas, arquivos temporários, pastas geradas automaticamente. Liste-os em um arquivo chamado .gitignore na raiz do projeto e o Git passa a ignorá-los.

.gitignore
# Senhas e configurações locais
.env

# Dependências e arquivos gerados
node_modules/
dist/

# Lixo do sistema operacional
.DS_Store
Thumbs.db

O site github/gitignore tem modelos prontos para cada linguagem.

ImportanteO .gitignore só vale para arquivos que ainda não foram commitados. Se você já enviou uma senha, veja a lição 3.8.
Nível 2 · Intermediário

Trabalhando em equipe

Agora você aprende a trabalhar em paralelo sem atrapalhar ninguém, juntar o trabalho de várias pessoas e corrigir erros sem medo.

2.1

Branches: linhas paralelas de trabalho

Uma branch (ramo) é uma cópia leve do projeto onde você pode experimentar sem mexer na versão principal (main). Quando o trabalho estiver pronto, você junta de volta.

Terminal
# Lista as branches (a atual aparece com *)
git branch

# Cria uma branch nova e já muda para ela
git switch -c feature/tela-login

# Volta para a main
git switch main

# Apaga uma branch que já foi juntada
git branch -d feature/tela-login
AnalogiaA main é o texto oficial de um livro. Uma branch é um rascunho em uma folha separada: você escreve à vontade e só copia para o livro quando estiver bom.

Em tutoriais antigos você verá git checkout -b. Ele faz o mesmo que git switch -c, que é a forma mais nova e clara.

2.2

Merge: juntando o trabalho

Para trazer o trabalho de uma branch para a main, vá para a main e faça o merge:

Terminal
git switch main
git pull                          # garante que a main está atualizada
git merge feature/tela-login
  • Fast-forward: se a main não mudou desde que a branch foi criada, o Git só “avança o ponteiro”. Nenhum commit extra é criado.
  • Merge commit: se as duas linhas mudaram, o Git cria um commit especial que une as duas histórias.

No dia a dia de equipe, o merge costuma acontecer pelo GitHub, através de um Pull Request (lição 2.4).

2.3

Resolvendo conflitos

Um conflito acontece quando duas pessoas alteram a mesma linha do mesmo arquivo. O Git não sabe qual versão escolher e pede a sua ajuda. Isso é normal e não quebra nada.

O arquivo fica marcado assim:

index.html
<<<<<<< HEAD
<h1>Bem-vindo ao sistema</h1>
=======
<h1>Olá! Faça seu login</h1>
>>>>>>> feature/tela-login
  1. Abra o arquivo. Acima de ======= está a sua versão atual (HEAD); abaixo, a versão que está chegando.
  2. Edite deixando o texto final como deve ficar e apague as linhas de marcação (<<<<<<<, =======, >>>>>>>).
  3. Marque como resolvido e finalize:
Terminal
git add index.html
git commit

# Se quiser desistir do merge e voltar ao estado anterior:
git merge --abort
DicaEditores como o VS Code mostram botões “Accept Current”, “Accept Incoming” e “Accept Both” em cima do conflito, o que facilita muito.
2.4

Pull Requests e revisão de código

Um Pull Request (PR) é um pedido para juntar sua branch na main, feito pelo GitHub. Ele abre um espaço para o time ver as mudanças, comentar, pedir ajustes e aprovar antes do merge.

  1. Crie uma branch, faça seus commits e envie: git push -u origin feature/tela-login.
  2. No GitHub, aparece o botão Compare & pull request. Clique nele.
  3. Escreva um título claro e descreva o que mudou e como testar.
  4. Peça revisão a colegas (Reviewers). Eles comentam linha a linha.
  5. Ajuste o que for pedido com novos commits na mesma branch; o PR atualiza sozinho.
  6. Com aprovação e testes passando, clique em Merge pull request e apague a branch.

E o fork?

Em projetos de outras pessoas onde você não tem permissão de escrita (como projetos open source), você faz um fork: uma cópia do repositório na sua conta. Você trabalha no fork e abre o PR dele para o projeto original.

2.5

Desfazendo coisas com segurança

SituaçãoComando
Descartar mudanças de um arquivo que não foi para o staginggit restore arquivo.txt
Tirar um arquivo do staging (mantém a edição)git restore --staged arquivo.txt
Corrigir a mensagem ou incluir algo no último commitgit commit --amend
Desfazer um commit que já foi enviado ao GitHubgit revert a1f3c2d
Desfazer o último commit local, mantendo as mudançasgit reset --soft HEAD~1
Apagar o último commit local e suas mudançasgit reset --hard HEAD~1
Regra de ouroSe o commit já foi enviado e outras pessoas podem ter baixado, use git revert: ele cria um commit novo que desfaz o anterior, sem reescrever o histórico. Use reset e --amend apenas em commits que ainda estão só no seu computador. E cuidado com --hard: ele apaga mudanças não salvas.
2.6

Guardando trabalho com stash

Você está no meio de uma tarefa e precisa trocar de branch para corrigir algo urgente, mas não quer fazer um commit pela metade. O stash guarda suas mudanças numa gaveta temporária.

Terminal
git stash push -m "tela de login pela metade"   # guarda
git switch main                                  # resolve a urgência...
git switch feature/tela-login
git stash list                                   # vê o que tem guardado
git stash pop                                    # traz de volta e remove da gaveta
2.7

Boas mensagens de commit

Uma boa mensagem explica o que mudou e, quando não for óbvio, por quê. Daqui a seis meses, você vai agradecer.

RuimBoa
ajustesfix: corrige cálculo de frete para CEPs do Norte
updatefeat: adiciona filtro por data no relatório de vendas
asdfdocs: explica como rodar o projeto no README

Muitas equipes usam o padrão Conventional Commits, com prefixos como feat (funcionalidade nova), fix (correção), docs, refactor, test e chore.

DicaPrefira commits pequenos e focados. Um commit = uma ideia. Fica mais fácil revisar, entender e desfazer.
2.8

Tags e releases

Uma tag marca um commit importante, geralmente uma versão publicada. É comum usar o padrão de versão semântica: v1.4.2 (maior.menor.correção).

Terminal
git tag -a v1.0.0 -m "Primeira versão em produção"
git push origin v1.0.0
git tag                     # lista as tags

No GitHub, em Releases → Draft a new release, você transforma uma tag em uma página de versão com notas do que mudou e arquivos para download.

Nível 3 · Avançado

Domínio do histórico e automação

Ferramentas para manter o histórico limpo, recuperar o que parecia perdido, achar bugs com precisão e automatizar a qualidade do projeto.

3.1

Rebase: reescrevendo a base da branch

O rebase pega os commits da sua branch e os reaplica em cima da versão mais recente da main. O resultado é um histórico em linha reta, sem commits de merge.

Terminal
git switch feature/tela-login
git fetch origin
git rebase origin/main

# Se houver conflito: resolva, depois
git add arquivo-resolvido.js
git rebase --continue

# Para desistir e voltar ao estado anterior
git rebase --abort
MergeRebase
HistóricoPreserva tudo como aconteceuLinear e mais limpo
Reescreve commits?NãoSim (novos hashes)
Seguro em branch compartilhada?SimNão
Regra de ouro do rebaseNunca faça rebase de commits que outras pessoas já baixaram. Se precisar enviar uma branch sua após o rebase, use git push --force-with-lease, que se recusa a sobrescrever trabalho alheio.
3.2

Rebase interativo: arrumando commits

Antes de abrir um PR, você pode juntar commits do tipo “wip”, “ajuste” e “agora vai” em um só, ou corrigir mensagens.

Terminal
git rebase -i HEAD~3   # edita os últimos 3 commits

O editor abre uma lista. Troque a palavra no início de cada linha:

editor
pick   a1f3c2d feat: cria tela de login
squash b72c9e1 wip
reword c09e4f3 corrige botao
  • pick: mantém o commit como está.
  • squash (ou s): junta com o commit de cima.
  • fixup (ou f): junta e descarta a mensagem.
  • reword (ou r): mantém, mas deixa editar a mensagem.
  • drop (ou d): remove o commit.
3.3

Cherry-pick: trazendo um commit específico

Precisa de só uma correção que está em outra branch, sem trazer o resto? O cherry-pick copia um commit específico para a branch atual.

Terminal
git switch release/1.4
git cherry-pick d4a8b10

Uso típico: levar uma correção urgente (hotfix) da main para uma versão que já está em produção.

3.4

Reflog: recuperando o que parecia perdido

Fez um reset --hard errado ou apagou uma branch? Calma. O Git guarda por um tempo (90 dias, por padrão) um registro de todos os lugares por onde o HEAD passou. Esse registro é o reflog.

Terminal
git reflog
# e3b1a90 HEAD@{0}: reset: moving to HEAD~3
# 7f2c118 HEAD@{1}: commit: feat: adiciona exportação CSV   ← o commit "perdido"

# Recria uma branch apontando para ele
git branch resgate 7f2c118
AnalogiaO reflog é o histórico de navegação do Git. Mesmo que você feche a aba, o endereço ainda está lá.

Atenção: o reflog só cobre o que foi commitado em algum momento e é local, ou seja, não vai para o GitHub.

3.5

Bisect: encontrando o commit que quebrou tudo

Algo funcionava na versão de mês passado e hoje não funciona, com 200 commits no meio. O bisect faz uma busca binária: em cerca de 8 testes você acha o culpado.

Terminal
git bisect start
git bisect bad              # a versão atual está com o bug
git bisect good v1.3.0      # esta versão funcionava

# O Git muda para um commit no meio. Teste e responda:
git bisect good             # ou: git bisect bad
# ...repita até ele mostrar o primeiro commit ruim

git bisect reset            # volta para onde você estava

Se você tiver um script de teste, git bisect run npm test faz tudo sozinho.

3.7

Automação com GitHub Actions

O GitHub Actions roda tarefas automaticamente a cada push ou PR: testes, verificação de estilo (lint), deploy. Basta criar um arquivo YAML na pasta .github/workflows/.

.github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  testes:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run lint
      - run: npm test

O resultado aparece como um ✓ verde ou ✗ vermelho no PR. Combinado com a proteção de branch (próxima lição), o GitHub impede o merge enquanto os testes não passarem.

3.8

SSH, segurança e proteção da main

Autenticação por chave SSH

Com SSH você não precisa digitar token a cada push.

Terminal
ssh-keygen -t ed25519 -C "seu.email@empresa.com"
cat ~/.ssh/id_ed25519.pub     # copie e cole em GitHub → Settings → SSH and GPG keys
ssh -T git@github.com         # testa a conexão

# Opcional: assinar commits com a mesma chave (selo "Verified")
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true

Proteção da branch main

Em Settings → Branches (ou Rules), crie uma regra para a main exigindo:

  • Pull Request antes do merge, com pelo menos uma aprovação;
  • Checagens do CI passando;
  • Bloqueio de push direto e de force push.

Um arquivo CODEOWNERS define quem precisa revisar cada parte do código automaticamente.

Vazou uma senha no commit?

Faça nesta ordem1) Troque a senha ou revogue a chave imediatamente: considere que ela já foi exposta. 2) Remova do histórico com uma ferramenta como git filter-repo. 3) Adicione o arquivo ao .gitignore. Apagar o arquivo num commit novo não basta, porque ele continua no histórico.

Para ir além

  • git worktree add ../hotfix main: trabalha em duas branches ao mesmo tempo, em pastas separadas.
  • Git hooks (ex.: com Husky): rodam lint e testes automaticamente antes de cada commit.
  • git blame arquivo.js: mostra quem alterou cada linha por último, e em qual commit.
